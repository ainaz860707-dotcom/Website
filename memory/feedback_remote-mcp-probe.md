Подключаешь remote-MCP по URL — до записи в `.mcp.json` пошли `POST` с `initialize` и прочитай ответ. `404` с телом про маршрут = эндпоинта нет. `401` с заголовком `www-authenticate: Bearer … resource_metadata=…` = сервер живой и ждёт авторизации, это правильный адрес.

**Why:** 2026-08-12, DataForSEO. README пакета `dataforseo-mcp-server@3.0.0` (опубликован накануне) называл remote-адресом `https://data.dataforseo.com/v3/mcp` — он отдавал `404 {"message":"The route v3/mcp could not be found."}`. Живым оказался `https://mcp.dataforseo.com/mcp`. **Паттерн ошибки:** npm-пакет и хостинг сервиса выкатываются раздельно, и документация регулярно описывает эндпоинт, которого ещё нет. **Исключённый тупик:** пробовать соседние адреса вслепую бесполезно — `https://data.dataforseo.com/mcp` тоже `404`; отличает живой адрес именно `www-authenticate`, а не код ответа сам по себе.

**How to apply:** цена проверки — одна команда `curl`, цена пропуска — мёртвый адрес в конфиге, где симптом («сервер не поднимается») указывает на клиента, а не на URL. Проверять до коммита, а не после жалобы владельца. Транспорт при выборе: remote-OAuth предпочтительнее stdio с логином и паролем в `env`-блоке — секреты не ложатся на диск (§4).
