# Визуальное объяснение

Владелец понимает картинку быстрее абзаца. Любое объяснение — сначала визуал, потом ≤5 строк текста под ним.

## Правило входа

Объясняешь устройство, последовательность, выбор, влияние правки или «было → стало» — этот навык обязателен.
Отвечаешь фактом в одну строку («да», «файл лежит там-то», «билд зелёный») — навык не нужен.

## Выбор формы (первое совпадение сверху)

| Что объясняешь | Форма | Инструмент |
|---|---|---|
| Поток, шаги, «что за чем» | flowchart / sequence | mermaid |
| Кто кого зовёт, зависимости, архитектура | graph LR | mermaid |
| Состояния объекта (заказ, заявка, сессия) | stateDiagram | mermaid |
| Сравнение вариантов, «было → стало» | таблица 2–4 колонки | markdown |
| Структура файлов/папок | дерево | markdown-блок |
| Числа по данным | график | навык `dataviz` |
| Схема + текст на 2+ экрана, владельцу нужно вернуться | страница | `Artifact` + навык `artifact-diagramming` |

## Как рисовать

- **Одна мысль — одна схема.** Больше 12 узлов — режь на две.
- **Подписи по-русски**, английские — только имена кода (`createLead`, `LeadInput`).
- **Показывай механизм, а не оглавление:** стрелки — реальные вызовы/переходы, а не «блок 1 → блок 2».
- **Красным (или пометкой) — то, что меняется** в правке; остальное — фон.
- Схема — по коду, который прочитал. Не помнишь связь — проверь `make_context_capsule`, а не рисуй догадку.

## Формат ответа

1. Схема/таблица.
2. Под ней — ≤5 строк: что здесь главное и что из этого следует для владельца.
3. Развилка внутри объяснения — оформляй по §1 CLAUDE.md: рекомендованный первым, с доказательством.

## Антипаттерны

- Абзац текста, а после него схема «для наглядности» — порядок обратный.
- Mermaid, повторяющий заголовки разделов вместо связей.
- Диаграмма ради диаграммы там, где хватило строки ответа.
